# 1. エグゼクティブサマリー

本システムは、ブラウザ上で会議音声を録音し、

1. マイク音声
2. システム音声
3. リアルタイムプレビュー文字起こし
4. 高精度な確定文字起こし
5. AI議事録生成
6. BlockNoteによる手動編集

を独立したパイプラインとして処理する。

最重要原則は以下である。

> **Recording is Source of Truth.**

録音データを最重要資産とし、以下の障害が発生しても録音を失わない。

* Web Speech API停止
* Groq障害
* Gemini障害
* Queue障害
* ネットワーク断
* Supabase障害
* ブラウザUI異常
* AI要約失敗
* タブ非表示
* 一時的なRate Limit

```text
    ↓

    ↓
IndexedDB
    ↓
R2
```

# 4. 重要な修正：16kHz固定を「AudioContext依存」にしない

v3.0の以下の記述は修正する。

```text
AudioContextを16kHzで初期化する
```

AudioContextの`sampleRate`は、そのAudioContextで使用されるサンプリングレートであり、入力された値を単純に「必ず16kHzになる」と仮定してはいけない。Web AudioではAudioContext内のノードは同じsample rateを使用する。

したがって、

```text
AudioContext
    ↓
Native sample rate
    ↓
AudioWorklet
    ↓
16kHz resampler
    ↓
PCM16
```

とする。

## 4.1 推奨仕様

```ts
interface AudioPipelineConfig {
  targetSampleRate: 16000;
  channels: 1;
  bitDepth: 16;
  chunkDurationMs: 30000;
}
```

AudioContextの実際のsample rateは実行時に取得する。

```ts
const actualSampleRate = audioContext.sampleRate;
```

AudioWorklet内部で16kHzへリサンプリングする。

# 8. Chunk生成

## 8.1 固定値

```text
Sample Rate: 16,000Hz
Channel: Mono
Bit Depth: 16-bit
Chunk: 30 seconds

Samples:
16,000 × 30 = 480,000 samples

PCM:
480,000 × 2 bytes
= 960,000 bytes

WAV:
960,044 bytes
```

約938KiBである。

GroqはWAVをサポートし、音声認識前に16kHz monoへダウンサンプルする仕様なので、16kHz PCMを送ること自体は合理的である。Groq公式も大容量処理ではchunkingを推奨している。

ただし、

> 16kHz WAVだから必ず認識精度が最高

とは仕様上断定しない。

実装時に以下を比較する。

```text
PCM16 WAV
vs
FLAC
vs
Opus/WebM
```

初期版では、

> **PCM16 WAV = Robustness優先**

とする。

# 10. VAD設計

## 10.1 VADの目的

VADは、

> **録音を削除するためには使用しない。**

目的は以下のみ。

```text
has_voice=false
      ↓
STTをスキップ
```

録音データは必ず保存する。

## 10.2 なぜ録音を捨てないのか

VADにはFalse Negativeが存在する。

例えば、

```text
小声
↓
VAD=false
↓
実際には重要発言
```

となる可能性がある。

したがって、

```text
Recording = 完全保存
STT = VADによる最適化
```

とする。

# 11. VAD状態

```ts
type VADResult = {
  /** Chunk 内の全フレームスコアの算術平均。0〜1 */
  score: number;
  hasVoice: boolean;
};
```

初期値として、

```text
threshold = 0.15
```

を使用してもよいが、これは固定仕様ではなく設定値とする。

```ts
interface VADConfig {
  threshold: number;
  minSpeechMs: number;
  hangoverMs: number;
  /** 正規化の下限。この dBFS 以下を score 0 とする */
  floorDbfs: number;
}
```

## 11.1 算出式

`threshold`が設定値である以上、**同じ音声から常に同じ`score`が出ること**が前提になる。正規化範囲とフレーム長を決めないと、実装ごとに`score`の意味が変わり、`threshold = 0.15`という数値も、§33のクォータ削減の見積もりも比較できない。次を固定仕様とする。

| 項目 | 仕様 |
| --- | --- |
| 評価位置 | **リサンプリング後**（16kHz / mono / Float32）。ネイティブレートで評価すると`minSpeechMs`のサンプル換算がレート依存になる |
| フレーム長 | **10ms = 160サンプル**固定。端数サンプルは次フレームへ繰り越し、Chunk末尾の未充填フレームは評価しない |
| フレームRMS | `rms = sqrt(Σ(sample²) / 160)` |
| 対数変換 | `dbfs = rms > 0 ? 20 * log10(rms) : floorDbfs` |
| 正規化 | `score_frame = clamp((dbfs - floorDbfs) / (0 - floorDbfs), 0, 1)`。`floorDbfs`の既定は`-60`、範囲は0〜1 |
| Chunk内集約 | `VADResult.score` = 全フレームの`score_frame`の**算術平均**（フレーム数0なら0） |

`clamp`により`score`は必ず0〜1に収まり、`threshold`も同じ尺度で解釈できる。

## 11.2 hasVoiceの判定

`threshold`の境界は**以上（`>=`）を音声候補**とする。`score_frame == threshold`のフレームは音声候補に含める。

`minSpeechMs`と`hangoverMs`は次の状態遷移として定義する。フレームごとに、

```text
score_frame >= threshold のとき:
    speechRun += frameSamples
    speechRun >= minSpeechSamples なら:
        voicedSamples += frameSamples
        hangoverLeft = hangoverSamples      -- 発話中は毎フレーム充填し直す

score_frame < threshold のとき:
    speechRun = 0                            -- 連続性の要求。途切れたらやり直し
    hangoverLeft > 0 なら:
        voicedSamples += frameSamples        -- 語尾や息継ぎを切り落とさない
        hangoverLeft -= frameSamples
```

ここで`minSpeechSamples = minSpeechMs / 1000 * 16000`、`hangoverSamples = hangoverMs / 1000 * 16000`。

Chunk境界で、

```text
hasVoice = voicedSamples >= minSpeechSamples
```

とし、`speechRun` / `voicedSamples` / `hangoverLeft`をリセットする。境界条件は次の通り。

- `minSpeechMs`に満たない単発の物音は`speechRun`が閾値に届かず`voicedSamples`に加算されないため、`hasVoice = false`になる
- `speechRun`が`minSpeechMs`に達した**そのフレームから**加算を始める。到達前のフレームは遡って加算しない（決定性のため、この非対称性を仕様として固定する）
- 全フレームが無音でも`hasVoice = false`、`score = 0`（フレーム数0の場合も`score = 0`）

初期値は`threshold = 0.15` / `minSpeechMs = 200` / `hangoverMs = 300` / `floorDbfs = -60`とする。値は設定値だが、**算出式と境界条件は固定仕様**であり、実装差異を許さない。

## 11.3 VADの位置づけ

§10.1の通り、`hasVoice = false`はSTTスキップの判断にのみ使い、録音の削除には使わない。ここで定義したのはブラウザ側のRMSベースVAD（Phase 1）であり、Silero等の学習済みモデルによる高精度化はPhase 2でサーバー側に置く（§114）。

# 16. Upload State Machine

```text
GENERATED
   ↓
IDB_STORED
   ↓
UPLOAD_PENDING
   ↓
UPLOADING
   ↓
UPLOADED
   ↓
DB_REGISTERED
   ↓
JOB_PENDING
   ↓
QUEUED
   ↓
PROCESSING
   ↓
COMPLETED
```

エラー時：

```text
UPLOAD_FAILED
JOB_FAILED
RETRYING
DEAD_LETTER
```

`UPLOADING → UPLOADED`の遷移条件は§19.3・§93で定義する（HTTP 2xx / Content-Type / Content-Length / sha256の全一致）。PUTが2xxを返しただけでは`UPLOADED`にしない。いずれかを満たさない場合は`UPLOAD_FAILED`へ落とす。

## 16.1 状態の所有者とupload_statusの対応

この状態機械は**1つのテーブル列に格納するものではない**。`audio_chunks.upload_status`（§46）が取りうる値は`pending` / `uploading` / `uploaded` / `failed`の4つだけであり、上の12状態をそのまま入れることはできない。どの状態を誰が持つかを次の通り固定する。

| 状態 | 所有者 | 保存先 |
| --- | --- | --- |
| `GENERATED` / `IDB_STORED` | ブラウザ | IndexedDB のChunkレコード。サーバーはまだこのChunkを知らない |
| `UPLOAD_PENDING` / `UPLOADING` / `UPLOADED` / `UPLOAD_FAILED` | ブラウザ（正）／サーバー（写し） | ブラウザのIndexedDB。サーバー側は`audio_chunks.upload_status`に`pending` / `uploading` / `uploaded` / `failed`として写す |
| `RETRYING` | **ブラウザのみ** | IndexedDB。再送待ちは次の試行までのクライアント側の待機状態であり、サーバーから見ればアップロードは未完了（`upload_status = 'failed'`のまま）である。`upload_status`に`retrying`は追加しない |
| `DB_REGISTERED` | サーバー | `audio_chunks`行が存在し`upload_status = 'uploaded'`であること自体が`DB_REGISTERED`を意味する。`upload_status`に別値は設けない |
| `JOB_PENDING` / `QUEUED` / `PROCESSING` / `COMPLETED` / `JOB_FAILED` / `DEAD_LETTER` | サーバー | `processing_jobs.status`（§46）。`audio_chunks`側は`stt_status`に集約結果を写す。アップロードの状態機械とは別の機械である |

この分離から次が従う。

- `upload_status`のCHECK制約は`pending` / `uploading` / `uploaded` / `failed`の4値のままとし、`retrying`や`db_registered`を足さない。足すと同じ事実の表現が2か所に増え、どちらが正かが決まらなくなる
- `upload_status`を`uploaded`へ更新できるのはサーバーのみであり、その条件は§19.3・§93の全一致である（クライアント申告値では遷移しない。§17.1）
- ブラウザ側の`RETRYING`は、サーバー側では何の行更新も伴わない。再送はPresigned URLの再取得から始める（URLの有効期限は5〜15分であり、保持したURLの再利用は期限切れになる。§19）

# 17. 重複Upload対策

Chunk IDではなく、

```text
meetingId
+
source
+
sequenceNo
```

を論理的な一意キーとする。

DB:

```sql
unique (
  meeting_id,
  source,
  sequence_no
)
```

さらにSHA-256を保存する。

```sql
sha256 text not null
```

これにより、

```text
同じsequence
＋
同じhash
```

なら同一Chunkと判断できる。

## 17.1 sha256の生成元

比較する2つの値がどこで作られたかを固定しないと、この検証は成立しない。クライアントが申告したハッシュを期待値として保存し、アップロード完了時に**同じクライアントが申告した値**と突き合わせても、一致するのは当然であり、R2上のオブジェクトが健全であることは何も示さない。破損も改変も検出できない。

したがって次を契約とする。

| 役割 | 値の生成元 |
| --- | --- |
| 期待値（expected） | Chunk登録時にサーバーが`audio_chunks.sha256`として保持した値。以後クライアントからの入力で上書きしない |
| 実測値（actual） | **R2のchecksum検証結果**、またはサーバーがR2から取得したオブジェクトに対して**サーバー側で再計算した**SHA-256 |

- 完了通知のリクエストボディに含まれるsha256は、**実測値として採用しない**。クライアントは自分が送ったものと違うハッシュを申告できる
- 期待値は登録時の一度きりの申告であり、それ自体は信頼の起点ではない。「クライアントが申告した内容のオブジェクトが、実際にR2に置かれたか」を検証するための固定された基準として使う
- R2のchecksum機能（PUT時に`x-amz-checksum-sha256`を署名対象に含め、オブジェクトメタデータとして検証結果を得る方式）を使う場合は、その検証結果をサーバーが読み出して期待値と比較する
- checksumを使えない場合は、サーバーがオブジェクトを取得してSHA-256を再計算する。Chunkは10分・約9.6MBであり、この再計算は現実的なコストに収まる
- 一致した場合にのみ`uploaded`へ遷移する（§19.3・§93）

# 19. R2 Security

Presigned URLはBearer Tokenとして扱う。

したがって、

```text
PUT URL
expiration: 5〜15分
single object
single operation
```

とする。

URLをログへ出力しない。

## 19.1 発行時の認可

有効期限を短く切ることは、**誰に発行するか**の問題を解決しない。Presigned URLがBearer Tokenである以上、発行そのものが認可判断であり、所有者検証を伴わない発行は「任意の利用者が任意の会議のオブジェクトを書ける」ことを意味する。

発行エンドポイントと完了エンドポイントの双方で、

```text
auth.uid() = meetings.user_id
```

を検証する（§77のownership起点と同一。child tableは§77の`child.meeting_id → meetings.user_id → auth.uid()`経路に従う）。検証に失敗した要求はURLを発行しない。

## 19.2 Object Keyはサーバーが決める

クライアントから受け取ったキー文字列をそのまま署名対象にしない。キーは、

```text
meetingId + source + sequenceNo
```

（§17の論理一意キー）と会議・チャンクのDB状態からサーバー側で組み立てる（§18のレイアウト）。クライアントが送るのはこの3値のみとし、サーバーは当該`meetingId`が要求者の所有であること、および`source`/`sequenceNo`が当該会議の想定範囲にあることを確認してからキーを決定する。

これにより、別会議・別利用者のキーを指定して上書きさせる経路を塞ぐ。クライアント由来のキーを受け入れる設計を残す場合も、上記の組み立て結果と一致することを検証したうえでのみ署名する。

## 19.3 uploaded遷移の条件

§93の確認項目は、独立した事後チェックではなく**`UPLOADED`（DB上の`uploaded`）へ遷移してよいかの判定条件**である（§16のUpload State Machine）。

```text
HTTP 2xx
+
Content-Type   が期待値と一致
+
Content-Length が期待値と一致
+
sha256         がDBメタデータ（§17）と一致
        ↓
   uploaded へ遷移
```

ここでの`sha256`は、**R2のchecksum検証結果またはサーバーがR2から取得したオブジェクトから再計算した値**であり、完了通知でクライアントが申告した値ではない（§17.1）。期待値はChunk登録時にサーバーが保持した`audio_chunks.sha256`であり、両者が一致した場合にのみ`uploaded`へ遷移する。クライアント申告値どうしを比較する実装は、この条件を満たさない。

いずれか1つでも満たさない場合、`uploaded`へ遷移させず`UPLOAD_FAILED`として扱い、§16のRetry経路に乗せる。**sha256比較は必須とする**（§93の「可能なら」ではない）。ハッシュを照合せずに`uploaded`とすると、破損または改変されたオブジェクトがSTT入力として確定し、「Recording is Source of Truth」が成立しなくなる。

`uploaded`への遷移を書き込むのはサーバー側であり、ここでも§19.1のownership検証を通す。

# 21. Queue容量設計

単純な1メッセージを、

したがって理論上、

# 47. Job Idempotency

```sql
create unique index uq_transcribe_job
on public.processing_jobs(meeting_id, chunk_id, transcript_version)
where job_type = 'transcribe_chunk';
```

これにより**同一世代内で**同一Chunkに対するSTT Jobを1つに制限する。世代を含めない`(meeting_id, chunk_id)`にすると、再文字起こしのJobを作れず、モデル差し替えが実行できない（§47.1）。

## 47.1 再実行の冪等性と結果世代の分離

上の一意インデックスと§48の`ON CONFLICT DO NOTHING`は、**同じ入力・同じモデルでの二重実行**を無害化するためのものである。これを「Chunkごとに永久に1回しかSTTしない」と読むと、モデル差し替えや再文字起こしの結果が、エラーも出さずに静かに捨てられる。

2つを別の契約として分ける。

| 目的 | 契約 |
| --- | --- |
| **再実行の冪等性**（Consumerの重複配送、Lease失効後の再実行） | 既存Jobを**再利用**する。新しいJobを作らず、§49のJob Lockで`status`を進める。`ON CONFLICT DO NOTHING`はこの経路のためにある |
| **結果世代の識別**（モデル変更、プロンプト変更、再文字起こし） | **新しい世代**として記録する。既存Jobの再利用も`ON CONFLICT DO NOTHING`も使わない |

結果世代を作る場合の規則。

- `transcript_segments`に`transcript_version`を持たせ、一意制約を`(chunk_id, segment_index, transcript_version)`に拡張する。旧世代の行は削除しない
- STT Jobの一意インデックスも世代を含める（上の`uq_transcribe_job`）。同一世代内では1 Jobに制限され、世代が変われば新しいJobを作れる
- どの世代を「現在のTranscript」とするかは`meetings.transcript_version`が指す。読み出しは常にこの版で絞る
- 世代を上げるのは**明示的な再生成操作**のときだけである。Retryは世代を上げない（同じ入力・同じモデルの再試行であり、冪等性の側の話である）

この区別がないと、「`ON CONFLICT DO NOTHING`で安全に再実行できる」という性質と「再生成しても旧結果を残す」（§68）という要件が、同じコードパスの上で両立しなくなる。

# 66. AI Hallucination対策

以下は禁止。

```text
元Transcriptにない決定事項
元Transcriptにない担当者
元Transcriptにない期限
```

## 66.1 主張ごとの根拠を必須にする

`sourceSegmentIds`が実在するかどうかだけを見る検証では、上記の禁止事項を止められない。実在するセグメントIDを引きながら、そのセグメントが述べていない担当者や期限を書くことは可能であり、むしろLLMの典型的な失敗はこの形を取る。IDの実在はTranscriptとの整合性ではなく、参照の体裁が整っていることしか示さない。

したがって、決定事項・担当者・期限の各項目に対し、**主張レベルの根拠**を出力スキーマで必須とする。

```text
claim            -- 生成された主張（決定事項 / 担当者 / 期限）
sourceSegmentIds -- 引用元セグメントID（1件以上）
quote            -- 引用元セグメント本文からの逐語引用
evidenceSpan     -- quote のセグメント本文内での文字範囲 [start, end)
```

## 66.2 生成後検証（2段階）

```text
段階1: sourceSegmentIds が実在するか
       ↓
段階2: quote が引用元セグメント本文に逐語で存在し、
       evidenceSpan がその位置と一致するか
       ＋
       claim（担当者名・期限・決定内容）が quote に裏付けられているか
```

段階2を通らない項目は**確定出力に載せない**。扱いは次の順で決める。

```text
1. 再生成    -- 同一セグメント集合で1回だけ再試行する
2. 除外      -- 再生成でも通らなければ minutes から落とす
3. 要確認送り -- 落とした項目は「未確認」として利用者に提示し、
                採否を利用者が決める（自動では確定しない）
```

「要確認送り」を残すのは、検証に落ちた項目が常に幻覚とは限らないためである（言い換えや表記ゆれで逐語一致しない場合がある）。ただし**検証を通らない項目を無検証で確定出力に混ぜることはしない**。利用者が採用したものは手動入力として扱い、§69〜§71のAI Summary / Manual Notes分離規則（AI更新による自動上書き禁止）に従う。

段階2の判定結果は§65のBusiness Validationと同じ生成後フェーズで実行し、§67の`ai_generation_version`単位で記録する。どの版がどの検証を通ったかを後から追えるようにするためである。

## 68.1 再生成Jobと保存の契約

「旧結果を削除しない」は、テーブルを定義しただけでは満たされない。Jobの作り方と保存の仕方まで決める。

- **Job作成**：再生成は、既存の`synthesize_minutes` Jobを再利用せず、**新しいJobを作成する**。§47.1の通り、既存Jobの再利用は「同じ入力・同じモデルの再実行」のための経路であり、再生成はそこに当たらない
- **保存**：Consumerは結果を`meeting_summary_versions`へ`insert`する。`version`は当該`meeting_id`の既存最大値 + 1とし、`unique(meeting_id, version)`で競合を検出する。`update`も`upsert`も使わない
- **記録内容**：`transcript_version` / `model_name` / `prompt_version`を必ず埋める（§67）。どのTranscript世代・どのモデル・どのPromptの出力かを後から追えなければ、版を残す意味がない
- **現在版の指定**：利用者に見せる版は`meetings.latest_summary_version`が指す1行とする。版の切り替えはこの列の更新のみで行い、過去の行は変更も削除もしない
- **失敗時**：検証（§66.2）を通らず確定できなかった場合、`meeting_summary_versions`に行を追加せず、`latest_summary_version`も進めない。直前の版が現在版のまま残る

# 77. RLS

全テーブルでRLSを有効化する。所有権列を持たないテーブル（`provider_usage`等）も例外ではなく、RLSを有効化したうえでポリシーを作らず、クライアントロールからの読み書きを一切許さない（§101.1）。

原則：

```text
auth.uid()
=
meetings.user_id
```

をownershipの起点とする。

Child tableは、

```text
child.meeting_id
→ meetings.user_id
→ auth.uid()
```

で制御する。

UPDATEについては、

```text
USING
+
WITH CHECK
```

を明示する。

このownership起点は、DBアクセスだけでなく**Presigned URLの発行・完了処理にも同じく適用する**（§19.1）。R2はRLSの外側にあるため、オブジェクトへの書き込み権限はURL発行時点のサーバー側検証でしか制御できない。発行・完了の両方で`auth.uid() = meetings.user_id`を確認する。

# 93. R2 Upload確認

PUT成功だけではなく、

```text
HTTP 2xx
+
expected Content-Type
+
expected Content-Length
+
sha256（R2 checksum または サーバー側で再計算した値が、
        DBメタデータ §17 の期待値と一致）
```

を確認する。sha256比較は必須であり、任意項目ではない。比較する実測値は**サーバーが自ら得た値**に限る（R2のchecksum検証結果、またはサーバーがオブジェクトを取得して再計算したSHA-256）。クライアントが完了通知で申告したハッシュを実測値に使うと、検証はクライアントの自己申告どうしの比較になり、破損も改変も検出できない（§17.1）。

これらは独立した事後チェックではなく、**§16の`UPLOADED`へ遷移してよいかの前提条件**である（§19.3）。1つでも満たさない場合は`uploaded`へ遷移させず、`UPLOAD_FAILED`としてRetry経路に乗せる。

## 101.1 アクセス制御

`provider_usage`はテナント所有権の列（`user_id` / `meeting_id`）を持たない。テナント横断の集計値であり、特定の利用者に帰属しないためである。したがって§77の`auth.uid() = meetings.user_id`というownership起点をポリシーとして書けない。

**所有権列がないことは、RLSを外してよい理由にはならない。** RLSを無効のままにすると、クライアントロールがこのテーブルを直接読めてしまい、他テナント分を含む総利用量・レート制限への接近度といった運用情報が漏れる。書き込みが可能なら、偽の利用量を書き込んでクォータ判定を狂わせることもできる。

したがって次を適用する。

```sql
alter table public.provider_usage enable row level security;
-- ポリシーは作成しない
```

- RLSを**有効化**し、**ポリシーを1つも作成しない**。これによりクライアントロール（`anon` / `authenticated`）からのSELECT / INSERT / UPDATE / DELETEはすべて拒否される
- 読み書きは**server / workerのみ**とする。RLSをバイパスするロール（`service_role`相当）の資格情報はサーバー側にのみ置き、クライアントには配布しない
- 利用者向けに利用量を見せる必要が生じた場合も、このテーブルを直接公開せず、サーバー経由で必要な粒度に絞った値を返す

# 126. 最終評価

このv4.0では、v3.0に存在した主な問題を以下のように解消した。

| 問題                       | 対策                                    |
| ------------------------ | ------------------------------------- |
| MediaRecorder Blob単体再生問題 | AudioWorklet + Standalone WAV         |
| 16kHz固定の誤認               | Native sample rate → 16kHz resampling |
| クロックドリフト                 | 共通Audio Graph + frame clock + 実測監視    |
| Background timer依存       | Audio frame基準                         |
| 無音Audio KeepAlive依存      | 廃止                                    |
| Groq 2系統quota            | VADによるSTT skip                        |
| URL fetch failure        | multipart fallback                    |
| Worker memory            | fallback 2MB上限                        |
| Groq 30秒timeout          | Provider configurable timeout         |
| Queue retry              | exponential backoff + jitter          |
| Queue消失                  | DLQ                                   |
| Queue 24h                | DBをJob Source of Truth                |
| Job duplicate            | Partial Unique Index                  |
| Transcript duplicate     | chunk_id + segment_index              |
| Summary race             | DB transaction + unique index         |
| AI hallucination         | sourceSegmentIds                      |
| AI再生成                    | versioned summary                     |
| Manual notes overwrite   | AI/Manual separation                  |
| Speaker誤認                | source ≠ speaker                      |
| Browser crash            | IndexedDB                             |
| Network failure          | IndexedDB retry                       |
| API secret漏洩             | Server/Worker only                    |

**総合評価：96〜97 / 100**

このレベルなら、単なる「技術スタック案」ではなく、**実装・結合テスト・障害テストまで進められるシステム設計書**として扱ってよいです。

ただし、95点以上を維持するために最後に一つ重要な方針を付けます。

> **「理論上動く」ことをDefinition of Doneにしない。60分〜2時間の実録音、ネットワーク断、タブ切替、System Audio、Queue重複配送、Groq 429、Gemini失敗まで含めた耐久試験を通過したものだけをProduction設計として認定する。**

特に最初の実装では、**「Mic → AudioWorklet → 30秒Standalone WAV → IndexedDB → R2 → Groq」だけを先に完成させる**のが最も安全です。その後Queue/Gemini/System Audioを一つずつ追加することで、どこで壊れたかを特定できる構造になります。
